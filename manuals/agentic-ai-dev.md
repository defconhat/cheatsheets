# 🤝 Агентная разработка с ИИ — шпаргалка

> **Agentic AI dev** — подход, при котором ИИ-агент (Claude Code, ZCode, Codex, Cursor, Devin) автономно или полу-автономно пишет, рефакторит и тестирует код через инструменты (Read/Write/Edit/Bash/Agent/…).
> Это НЕ чат-бот: агент работает в реальном репозитории, видит файлы и выполняет команды.

---

## 🧭 Ментальная модель

```
┌──────────────────────────────────────────────────┐
│  Ты (человек) — постановщик задач и ревьюер       │
│                       │                          │
│                       ▼                          │
│    ┌─────────────────────────────────────┐        │
│    │  ИИ-агент (ZCode / Claude Code)     │        │
│    │  — LLM + контекст + инструменты      │        │
│    └──────┬──────────────────────────────┘        │
│           │                                       │
│      ┌────┴─────┬─────────┬──────────┐            │
│      ▼          ▼         ▼          ▼            │
│   Read/Write  Edit     Bash      Agent(субагент)  │
│   (файлы)    (правки)  (shell)   (подзадача)      │
│      │          │         │          │            │
│      ▼          ▼         ▼          ▼            │
│                  РЕПОЗИТОРИЙ + тесты + CI          │
└──────────────────────────────────────────────────┘
```

**Человек**: пишет ТЗ, ревьюит, направляет.
**Агент**: исследует код, планирует, пишет, тестирует, итерирует.

## 🧩 Анатомия хорошего промпта (задачи агенту)

| Часть | Что | Пример |
|---|---|---|
| **Цель** | Что сделать, зачем | «Добавить экспорт пользователей в CSV» |
| **Контекст** | Где, какие файлы | «В `src/api/users.py`, использовать существующий `User` model» |
| **Ограничения** | Чего НЕ делать | «Не трогать auth, не добавлять новые зависимости» |
| **Критерий успеха** | Как проверить | «`pytest tests/test_users.py` проходит, эндпойнт `/export` отдаёт CSV» |
| **Стиль** | Конвенции | «PEP8, тайпинги, docstrings на русском» |

### Плохой промпт ❌
> «сделай красиво»

### Хороший промпт ✅
> «В проекте `myapi` (FastAPI, см. `src/api/`) добавь эндпойнт `GET /users/export.csv`. Должен отдавать CSV со всеми пользователями (`User` model из `src/models.py`). Колонки: id, email, created_at. Покрыть тестом в `tests/test_users_export.py`. Не менять auth-слой. Запусти `pytest` и убедись, что всё зелёное.»

## 🔄 Цикл работы с агентом

```
1. Описание задачи (ты)
        │
2. Агент исследует код (Read, Grep, Glob)
        │
3. Агент планирует (Plan Mode / ExitPlanMode)
        │
4. Ты одобряешь план (или корректируешь)
        │
5. Агент реализует (Write, Edit, Bash)
        │
6. Агент проверяет (тесты, линтер, сборка)
        │
7. Ты ревьюишь diff
        │
8. Итерация (если нужно) → шаг 5
        │
9. Коммит / PR
```

## 🛠️ Инструменты агента (как ими пользоваться)

| Инструмент | Когда просить/ожидать |
|---|---|
| **Read** | Чтение файла перед изменением |
| **Grep / Glob** | Поиск по кодовой базе |
| **Edit** | Точечная правка существующего файла |
| **Write** | Создание нового файла |
| **Bash** | Запуск тестов, миграций, сборки |
| **Agent (субагент)** | Делегирование подзадачи (например, «найди все места вызова X») |
| **WebSearch / WebFetch** | Поиск в доках библиотеки |
| **TodoWrite** | Ведение чек-листа сложной задачи |

### Подсказки агенту
- «Сначала изучи код, потом предложи план».
- «Используй субагента для поиска всех вызовов этой функции».
- «Не предполагай — прочитай файл перед изменением».

## 📋 Паттерны задач для агентов

### 1. Feature (новая функциональность)
```
Добавь <фичу> в <модуль>.
Контекст: <как устроено сейчас>.
Успех: <как проверить>.
```

### 2. Bugfix
```
Воспроизведи: <шаги>.
Ожидание: <что должно быть>.
Реальность: <что происходит>.
Найди root cause и пофикси. Добавь регрессионный тест.
```

### 3. Рефакторинг
```
Вынеси <дублирование> в <общую функцию>.
Не меняй поведение — все существующие тесты должны оставаться зелёными.
```

### 4. Тесты
```
Покрой тестами <модуль>.
Используй pytest, fixtures из conftest.py.
Цель — покрыть happy path + 2-3 граничных случая.
```

### 5. Документация
```
Обнови README после последних изменений.
Допиши docstrings к публичным функциям в <файле>.
```

### 6. Миграция / перевод
```
Переведи <модуль> с <старая либа> на <новая>.
Сохрани API. Покрой миграцию тестом.
```

### 7. Code review
```
Просмотри diff в ветке feature/X.
Найди: баги, race conditions, утечки, нарушение конвенций.
Предложи фиксы, но не применяй.
```

## 🧠 Управление контекстом

Контекст агента ограничен (от 100k до 1M токенов). Переполнение = деградация.

### Правила
| Приём | Зачем |
|---|---|
| **Точечные промпты** | Не «перепиши весь проект», а «исправь функцию X» |
| **Plan Mode** | План экономит токены — не даёт агенту уйти не туда |
| **Субагенты (Agent tool)** | Делегируют подзадачи — их контекст не засоряет основной |
| **`/compact`** | Сжатие длинной сессии в summary |
| **`/clear`** | Полный сброс при смене задачи |
| **AGENTS.md / CLAUDE.md** | Постоянные правила — не повторять каждый раз |
| **Маленькие коммиты** | Каждый коммит = атомарная задача → легче откатить |

### Симптомы переполнения контекста
- Агент «забывает» ранние инструкции.
- Повторяет уже сделанные шаги.
- Начинает галлюцинировать имена файлов/функций.
→ `/compact` или `/clear` + краткий recap.

## 📐 План-мод (Plan Mode)

Перед сложной задачей — проси план:

```
Изучи кодовую базу и предложи план рефакторинга X.
Пока не делай изменений — только план.
```

Агент использует **EnterPlanMode / ExitPlanMode**: исследует, формирует план, показывает тебе, ты одобряешь → только потом правит.

**Плюсы:**
- Экономит токены (нет «пробных» правок).
- Ты видишь направление до того, как код изменён.
- Легко скорректировать подход.

## 🗂️ AGENTS.md / CLAUDE.md — инструкции проекта

Файл с правилами, который агент читает в каждой сессии.

### Структура (рекомендация)
```markdown
# Project: myapi

## Стек
- Python 3.12, FastAPI, SQLAlchemy 2.0, pytest.
- БД: PostgreSQL 16.
- Деплой: Docker + GitHub Actions.

## Конвенции
- PEP8, type hints обязательны.
- Имена функций: snake_case.
- Имена классов: PascalCase.
- Коммиты: conventional commits (feat:, fix:, refactor:…).

## Архитектура
- Слои: api → service → repository.
- Не обращаться к БД из api-слоя.
- Все SQL — через SQLAlchemy, без сырого SQL.

## Тесты
- pytest tests/ перед PR.
- Покрытие новых функций ≥ 80%.

## Не делать
- Не добавлять зависимости без обсуждения.
- Не менять схему БД без миграции Alembic.
- Не коммитить .env и секреты.
```

### Скоупы (для ZCode)
- **`~/.zcode/AGENTS.md`** — личные дефолты (язык, стиль).
- **`<repo>/AGENTS.md`** — правила проекта (версионируется).
- Workspace переопределяет user при конфликте.

## 🔌 Расширение агентов

| Расширение | Что даёт |
|---|---|
| **MCP** | Внешние инструменты (БД, API, браузер, Jira, Slack) |
| **Skills** | Готовые сценарии (создание PDF, ревью кода) |
| **Slash commands** | Параметризованные шаблоны промптов |
| **Hooks** | Перехват событий (PreToolUse → валидация/логирование) |
| **Subagents** | Изолированные подзадачи с своим контекстом |

### Пример: MCP для БД
Подключив MCP-сервер PostgreSQL, агент может сам выполнять запросы, читать схему, объяснять данные — без копирования в чат.

## ✅ Чек-лист перед PR от агента

- [ ] **Тесты проходят** (агент запускал, ты проверил вывод).
- [ ] **Diff осмысленный** — нет мусора (дебаг-принтов, закомментированного кода).
- [ ] **Нет секретов** в коде/коммитах.
- [ ] **Конвенции соблюдены** (линтер, форматтер).
- [ ] **Документация обновлена** (README, docstrings, если API изменилось).
- [ ] **Нет регрессий** — смежные тесты тоже зелёные.
- [ ] **Коммиты атомарны** и с осмысленными сообщениями.

## ⚠️ Типичные ошибки (антипаттерны)

| Антипаттерн | Почему плохо | Как надо |
|---|---|---|
| **«Сделай всё»** | Агент растекается, контекст переполняется | Декомпозируй на маленькие задачи |
| **Слепое доверие diff** | Агент может «починить» и сломать другое | Читай diff, гоняй тесты |
| **Игнорирование plan mode** | Тратишь токены на неверный путь | Сначала план, потом код |
| **Хардкод в промпте** | «Поменяй порт на 8080» — магическое число | «Прочитай конфиг, используй переменную» |
| **Молчаливое слияние** | PR без ревью = отсутствие человека | Ревью обязателен, как от коллеги |
| **Большие задачи в один заход** | Контекст портится, ошибки множатся | 1 задача → 1 коммит → 1 PR |
| **Не читать историю** | Агент может повторить отвергнутый подход | Скажи «такое уже пробовали, не сработало» |

## 🎚️ Уровни автономности

| Уровень | Поведение | Когда |
|---|---|---|
| **Manual (ask)** | Каждое действие — с разрешения | Опасные операции (deploy, миграции БД) |
| **Auto-edit** | Файлы правит сам, shell — спрашивает | Обычная разработка |
| **Plan-first** | Сначала план, потом код | Сложные фичи, рефакторинг |
| **Yolo / hands-off** | Всё автоматически | Только в sandbox/throwaway экспериментах |

> Для прода — **Plan-first + ревью diff**. Yolo — только в изолированной VM.

---

## 🔐 Безопасность

| Риск | Митигация |
|---|---|
| **Удаление файлов** | Permission mode, hooks на `PreToolUse` для rm/mv |
| **Коммит секретов** | `.gitignore` для `.env`, pre-commit hook на detect-secrets |
| **Внешние вызовы** (curl, SSH) | Явное разрешение, sandbox-сеть |
| **Выполнение произвольного кода** | Не запускать агента на `sudo`, контейнер/VM для недоверенного |
| **Утечка через WebSearch** | Не просить искать внутренние URL/данные |

---

## 📊 Метрики эффективности

- **Время до первого теста** — агент должен быстро дать что-то запускаемое.
- **Кол-во итераций до зелёных тестов** — если >5, пересмотри ТЗ.
- **Доля кода в финальном PR** — если <50% выжило, план был плохой.
- **Токены на задачу** — следи за стоимостью через `/cost`.

## 🧪 Продвинутые приёмы

### 1. «Переведи код в тест, потом в реализацию» (TDD)
```
Напиши тесты для функции X (пока без реализации).
Покажи мне тесты.
Потом реализуй так, чтобы тесты прошли.
```

### 2. Много-агентный подход
- Один агент — реверс-инженерит существующий код.
- Другой — пишет новую фичу на основе документации первого.
- Третий — ревьюит diff.

### 3. «Покажи 3 варианта»
```
Предложи 3 архитектурных подхода к задаче.
Сравни по сложности, поддержке, производительности.
Я выберу — потом реализуй.
```

### 4. Использование памяти (ZCode)
- `/remember` для фактов о проекте («порт — 4000», «используем zsh»).
- Память подгружается автоматически в будущих сессиях.

### 5. Субагенты для параллельных задач
```
Запусти 3 субагента параллельно:
1. Найди все use-cases функции deprecated_api().
2. Проанализируй логи ошибок в /var/log/app/.
3. Найди дублирующийся код в src/services/.
```

## 💡 Золотые правила

1. **Маленькие задачи, частые коммиты.** Большой PR от агента = боль.
2. **Сначала план.** Plan Mode экономит время и токены.
3. **Ревью как от коллеги.** Не доверяй вслепую — гоняй тесты, читай diff.
4. **AGENTS.md — твой «.bashrc» для агента.** Пропиши конвенции один раз.
5. **Контекст — конечный ресурс.** Компакти и чисти сессии, декомпозируй задачи.
6. **Человек — руль.** Агент — мощный инструмент, но решение за тобой.
